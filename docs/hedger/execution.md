# hedger 执行细节

## 组件

| 组件 | 文件 | 职责 |
|---|---|---|
| `Service` | `service.go` | 进程生命周期：数据库、gateway 推送、定时任务（每 2 秒对账、资金费估算、行情订阅回收） |
| `Engine` | `engine.go` `commands.go` | 命令入口（开、平、补腿、减腿、全平、撤销）；为每个执行中的动作启动一个 runner；结算组状态 |
| `runner` | `runner.go` | 一个动作的事件循环：下单、合并交易所回报、查单、对冲、结束 |
| `Market` | `market.go` | gateway 推送的本地缓存：盘口、资金费率、账户持仓与推送状态 |
| `Store` | `store.go` | PostgreSQL 读写 |
| 纯函数 | `sizing.go` `position.go` `view.go` | 数量计算、比例、持仓推导、视图 |

## 开仓

1. **解析两条腿**（`resolveLeg`）：标的存在；账户已启用、`markets` 含该市场、路由含该标的；取路由规则。
2. **校验**：方向必须一多一空；两条腿不能是同一账户上的同一标的；限价模式需要挂单腿与正的限价、有效方式为 GTC 或只做 Maker。
3. **计算比例**（`MatchLegs`）与**数量**（`PlanSize`）：
   - 输入按腿 1 的币数量，或按每条腿的金额（计价货币）。
   - 两腿都按各自账户的步长**向下取整**；按数量匹配时，由步长更粗的一腿驱动另一腿，保证任何一条腿都不超过请求的大小。
   - 取整造成的名义差额（数量偏差）在下单前显示。
   - 低于任一腿的最小数量或最小金额时拒绝，并说明是哪条腿、差多少。
4. **写库**：创建组、两条腿、开仓动作（状态 `opening`），写一条 `event.opening` 日志。
5. **启动 runner**。

## 两种执行方式

### 双边市价

两条腿同时下市价单。动作在两笔订单都终结后结束：两腿都完全成交为 `done`；否则 `failed`，并逐条腿说明成交了多少、为什么（交易所原因）。

### 限价 + 对冲

- 挂单腿下限价单（可选只做 Maker；**只作用于挂单**）。
- 挂单每成交一部分，立即在另一条腿按比例下市价对冲单，使敞口最多是「一笔成交」。
- 挂单完全成交后，对冲腿直接补到目标数量，不留舍入零头；剩余量低于对冲腿的最小下单量时保留并记日志。
- 撤销时撤掉挂单，已成交的部分已经对冲。
- **对冲单被拒时立即撤掉挂单并停止**，不会继续累积敞口。

## 下单安全

1. **先写后发**：每笔订单先写入 `hedge_orders`（状态 `sending`），再发送。进程在发送途中崩溃，重启后凭 clientOrderId 就能查明订单是否存在。
2. **结果未知（`unknown`）**：标记为 `unknown`，按 0.5、1.5、3、5 秒的节奏按 clientOrderId 查询，**绝不重下**。
3. **`not_found`** 只在下单 10 秒后才采信（刚发出的订单可能还没被索引），之后订单记为 `not_found`（从未下出）。
4. **`unconfirmed`**（交易所既不能显示也不能否认）：用该订单的当前挂单与成交记录确认：
   - 在挂单里：继续跟踪；
   - 有成交：按成交定（全部成交 = `filled`，部分 = `canceled` 余量）；
   - 2 分钟内两者都找不到：订单记为 `unresolved`，动作停止，组标记为未对冲，**不做自动修复**（腿的真实数量未知），由交易员先去交易所核对再补腿、减腿或全平。
5. **异步拒单**：经纪账户先返回 `pending`，拒单随后经推送到达，带 `rejectCode` / `rejectMessage`。**与同步拒单同样处理**：对冲单被拒立即停止动作（不会再补发对冲单），开仓腿被拒按失败策略处理。
6. **重启接管**：进程重启后，每个执行中的动作重新接管，先按 clientOrderId 核对全部订单再继续；市价动作中某条腿还没下单的，补下这一条腿。
7. **以交易所为准**：订单状态由账户推送实时更新，另有每 5 秒的定时查询兜底；推送在线时降低查询频率。
8. **补齐成交**：动作结束后从交易所拉取成交记录，补齐手续费与精确成交价。
9. 查单的定时任务随 runner 结束而停止，不会在动作结束后继续运行。

## 一条腿失败时

开仓时选择失败策略：

| 策略 | 行为 |
|---|---|
| `unwind`（回退另一条腿，默认） | 自动把多出的那条腿减到与另一条腿相同（一条腿完全没成交时就是全部平掉）；平仓动作同理，自动补完。自动修复只做一次，再失败就停在未对冲等人处理 |
| `hold`（保留并提醒） | 保留，标记未对冲，由交易员决定补腿（把少的那条腿补足）、减腿（把多的那条腿减少）或全平 |

**有订单结果无法确认时，两种策略都跳过自动修复**，并在日志中说明。

## 与交易所对账

对冲的持仓由 hedger 自己的订单推导；交易所的仓位来自账户推送。每 2 秒检查一次所有空闲的 `open` 组：

- 只比较永续腿（现货是余额，不是仓位）；只在该账户推送在线时比较。
- 交易所在腿的方向上持有的数量**少于**对冲记录（容差一个步长），并且**持续 20 秒**（成交与仓位走不同的推送，可能短暂交错），组就标记为未对冲，日志写明哪条腿、交易所持有多少、对冲记录多少。
- 常见原因：在交易页手动平了这条腿、被强平、自动减仓。
- 交易所持有**更多**不算异常（同一账户可能有对冲之外的仓位），只在界面提示。
- gateway 推送断开时清空缓存的持仓与账户在线状态，避免用过期数据对账。

交易所风控引擎下的订单（`origin`：liquidation / adl / settlement）会记到涉及该账户与标的的每个活跃组的日志里（按订单与状态去重），说明为什么仓位变了。

## 平仓与修复

| 操作 | 目标数量 |
|---|---|
| 平仓 `close` | 腿 1 按比例取整到步长；腿 2 = 腿 1 × 比例，取整到腿 2 的步长；可市价或限价 + 对冲 |
| 补腿 `rehedge` | 市价补足较小的一条腿，回到完整规模 |
| 减腿 `trim` | 市价减少较大的一条腿，与较小的一条匹配 |
| 全平 `unwind` | 两条腿全部市价平掉 |

两腿差额小于较小一条腿的步长时视为平衡，不允许补腿或减腿。

## 资金费估算

每次结算时，按「结算时的报价费率 × 持有量 × 价格」估算每条腿的资金费，写入 `hedge_funding`（按组、腿、结算时刻去重）。

## 就绪检查

`GET /v1/health` 在数据库可用**且** gateway 推送在线时返回 `ok:true`，否则 503 并给出原因。
