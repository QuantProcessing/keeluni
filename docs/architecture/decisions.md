# 设计决策

这里记录塑造系统形状的关键决策，以及为什么这样定。每条决策都在代码与测试中有对应的约束。

## 交易与账户

| # | 决策 | 原因 |
|---|---|---|
| A1 | **幂等只靠交易所的 clientOrderId。** gateway 不重试、不落库；结果未知时只查不重下 | 重试与本地账本都会在网络抖动时制造重复订单；交易所是唯一能证明订单存在的地方 |
| A2 | **标的身份不随账户变化。** `binance:perp:BTC-USDT` 无论经原生账户还是 Gate CrossEx 交易，都是同一个标的 | 行情、K 线、资金费率只属于订单簿；把账户编进标的会让同一个市场出现多份行情 |
| A3 | **经纪账户是一种账户，不是页面或模式。** 没有单独的 CrossEx 页面，也没有全局模式切换 | 用户想交易的是市场；"用哪个账户"是下单时的一个选择 |
| A4 | **同一交易所允许原生账户与经纪账户并存** | 两者的资金池、规则、费率不同，各有用途 |
| A5 | **从不在背后切换账户。** 记住每个交易所上次选择的账户，但候选账户变化时只清空，不替换 | 账户决定资金归属，必须由用户显式决定 |
| A6 | **下单规则取自账户的路由**（tick、step、最小数量、最小金额） | CrossEx 的规则可能比交易所原生更细或更严，按交易所规则校验会误拒或误放 |
| A7 | **不提供修改账户模式、持仓模式、保证金模式的功能**，只读取并遵守 | 这些设置在交易所之间语义不一致，改错会影响账户上的其他仓位 |
| A8 | **只支持单向持仓**；双向持仓账户接入时提示、下单时本地拒绝 | 规范化模型是每个市场一个带符号的净仓位 |

## gateway

| # | 决策 | 原因 |
|---|---|---|
| G1 | **gateway 是交易所的唯一出口** | 限流与连接只有集中管理才能保证下单不被后台任务挤掉 |
| G2 | **gateway 只持有可重建的当前事实，不需要数据库** | 交易链路不应依赖任何应用的存储；重启即可恢复 |
| G3 | **规范化，不做业务** | 业务（对冲、套利）各自演进，拥有自己的存储与发布节奏 |
| G4 | **后台采集最多占交易所额度的 25%，拿不到就跳过本轮** | 采集是"尽力而为"，不能和下单、用户查询争抢 |
| G5 | **一个 (频道, 标的) 只有一个上游订阅**，延迟 30 秒关闭 | 页面刷新不应反复开关交易所连接 |
| G6 | **持仓与余额推送完整快照**，前端直接替换 | 增量合并在断线重连时容易出错；完整快照天然可修复 |

## 资金费率

| # | 决策 | 原因 |
|---|---|---|
| F1 | 统一为 **rate（单次结算比例）+ intervalHours + apr（单利年化）** | 每小时、每 4 小时、每 8 小时结算的交易所只能通过年化比较 |
| F2 | **周期未知时不给周期、不给年化，绝不默认 8 小时** | 错误的默认值比缺失更危险 |
| F3 | 资金费率是 gateway 的**常驻数据集**，交易页与对冲页只有这一个来源 | 避免两条采集路径给出不同的数字 |

## 对冲

| # | 决策 | 原因 |
|---|---|---|
| H1 | **对冲是一个应用**，有自己的 PostgreSQL；gateway 不知道对冲的存在 | 对冲需要积累历史（订单、成交、资金费），按 G2 不能放在 gateway |
| H2 | **持仓由订单推导，不单独存储** | 重启、丢包、推送缺失都不会让 hedger 相信一个交易所并不持有的仓位 |
| H3 | **两条腿必须一多一空** | 去掉无意义的同向组合，界面只需一个"交换多空"按钮 |
| H4 | **腿的账户没有默认值** | 同 A5 |
| H5 | **比例由后端根据合约倍数计算**（1000PEPE、kPEPE…），前端不推断 | 比例决定之后所有平仓、补腿的数量，必须只有一个来源 |
| H6 | **结果无法确认时不自动修复** | 腿的真实数量未知时，按自己的账本修复可能让敞口更大 |
| H7 | **交易所持仓少于对冲记录时标记为未对冲**（持续 20 秒）；多于时只提示 | 少于说明腿被外部平掉、强平或减仓；多于可能只是账户上的其他仓位 |
| H8 | **对冲腿的仓位在交易页可以平，但会警告** | 不阻止用户处理紧急情况，但让后果清楚 |

## 产品与期权

| # | 决策 | 原因 |
|---|---|---|
| P1 | **产品集合开放**：每层对 `Product` 分支，未知产品视为不支持；新增产品是纯增量 | 大宗商品等后续产品不需要改动已有产品的代码路径 |
| P2 | **期权数量以标的计，价格以权利金资产计，希腊值以行权价币种计**，所有交易所一致 | 下单用交易所的单位；风险用交易员衡量的单位；两者不混 |
| P3 | **gateway 只发布单个期权的事实**（价格、IV、希腊值、到期日的远期与偏斜）；组合风险在 optioner | 跨持仓的计算属于应用（G3） |
| P4 | **希腊值统一用 Black-76 在 gateway 计算**，不直接透传交易所的数字 | 有的交易所不发布；统一计算后各交易所可比。实测与 Deribit 发布值一致到第四位小数 |
| P5 | **币本位期权的 Delta 计入权利金所持有的币** | 否则一个"Delta 中性"的币本位组合在美元上并不中性 |
| P6 | **期权只用限价单**；市价对冲腿只用于永续与现货 | 期权盘口薄，市价单会被吃穿 |
| P7 | **多腿组合是独立订单**，按腿报告状态；`partial` 明确告诉用户组合不完整 | 范围内的交易所没有原子组合订单簿，不能假装原子 |
| P8 | **optioner 不用数据库** | 期权风险全是交易所的当前事实；执行记录带 clientOrderId，重启后交易所即事实 |
| P9 | **期权不进入 `/v1/instruments` 的默认列表** | 数千个合约属于期权链界面，不属于市场选择器 |
| P10 | **Kraken 现货与期货是一个账户的两套 Key**，各自可选 | Kraken 的两个平台密钥独立；用户应能只连接其中一个 |

## 品牌与界面

| # | 决策 | 原因 |
|---|---|---|
| U1 | 视觉与交互参照 Hyperliquid：紧凑表格、不用卡片、颜色只表示涨跌与操作 | 交易终端的信息密度与可读性优先 |
| U2 | 默认中文，可切换英文；交易所原文与名称不翻译 | 主要用户使用中文；交易所原文是排查问题的证据 |
| U3 | 后端发给用户的消息用"编码 + 参数"，前端按语言渲染 | 同一条日志能以两种语言显示，旧记录仍可读 |
